## 5. Sincronización FIFO

- [x] 5.1 Implementar `useOfflineIncidentSync()` (`features/incidents/hooks/useOfflineIncidentSync.ts`): orquestación FIFO (`listPending()` → por cada entrada, `markSyncing` → reconstruir payload y evidencias desde `photoBlobs` → `useCreateIncident().mutateAsync` → `markSynced` o `markError`), un solo intento a la vez. **Bug real encontrado y corregido durante esta tarea:** el ciclo re-leía `listPending()` (que sigue incluyendo `status: 'error'`) y tomaba `pending[0]` de nuevo en cada iteración, sin excluir entradas ya intentadas en el mismo ciclo — una entrada recién fallida volvía a ser `pending[0]` indefinidamente (reintento en caliente dentro del mismo ciclo, en vez de pasar a la siguiente). Corregido con un `Set` de IDs ya intentados por ciclo; un ciclo *futuro* (online/sync/retry) sigue pudiendo reintentar una entrada en error, que es el comportamiento correcto.
- [x] 5.2 Exponer `pendingCount`, `syncingId` y `retry(localId)` desde el hook. También se agregó `notifyEnqueued()` (llamado por el formulario tras un `enqueue()` exitoso) para refrescar el badge de inmediato y disparar sync ya mismo si el dispositivo ya está online (cubre el caso "falló por red pese a `navigator.onLine === true`").
- [x] 5.3 Registrar el listener del evento `online` del hilo principal para disparar el ciclo de sincronización.
- [x] 5.4 En `src/sw.ts`, registrado `self.addEventListener('sync', ...)` con tag `sync-incidents` (implementado en la tarea 1.2 junto con la migración a `injectManifest`): al recibir el evento, hace `self.clients.matchAll()` y `postMessage({ type: 'sync-incidents' })` a cada cliente — sin ningún `fetch` a `/api/**` desde dentro del Service Worker (design.md D3/D4). Las constantes de tag/tipo de mensaje viven en `src/lib/offlineSyncMessage.ts`, compartidas entre `src/sw.ts` (lib WebWorker) y el hilo principal (lib DOM) sin conflicto de `tsconfig`.
- [x] 5.5 En el hilo principal, escucha el mensaje `sync-incidents` del Service Worker (`navigator.serviceWorker.addEventListener('message', ...)`) y dispara el mismo ciclo de sincronización que el listener `online`.
- [x] Tests: `useOfflineIncidentSync.test.ts` (4 tests, todos pasan) — FIFO al montar online, un fallo no bloquea al siguiente, `retry()` re-sincroniza, `pendingCount` refleja `pending`+`error`. Se agregó también una guarda de desmontaje (`isMountedRef`) para que un ciclo en curso no siga tocando estado de React ni arranque entradas nuevas tras desmontar el componente (p. ej. el usuario navega fuera de `/m/incidentes/nuevo` a mitad de sync) — la entrada ya en vuelo se deja terminar, sin abortar el request a mitad. `t`/`userId`/`createMutation` se leen vía ref dentro de los callbacks estables (`syncOne`/`runSyncCycle`), no como dependencias de `useCallback`, para que los efectos que dependen de ellos no se re-suscriban en cada render.
