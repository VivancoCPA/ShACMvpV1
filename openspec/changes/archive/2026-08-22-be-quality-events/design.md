## Context

`ShcMvpEndPoint` tiene hoy tres módulos de dominio reales: Incidentes SyST (M3, `be-incidentes-catalogos`, archivado), No Conformidades (M2, `be-no-conformidades`) y los catálogos Áreas/Locales/Zonas. Todos siguen el mismo patrón VSA: `Features/<Modulo>/<Accion>/{Command,Endpoint,Handler,Validator}.cs`, entidades en `ShcMvpEndPoint.Domain/Entities`, CQRS (Dapper para `GET`, EF Core para mutaciones), multi-tenancy filtrando por `empresaId` de la sesión activa con 404-nunca-403, numeración correlativa vía `EmpresaSecuencia`.

Este cambio agrega el cuarto y más complejo módulo: Quality Event (M4). A diferencia de Incidentes y NC, QE depende de ambos: puede originarse de un Incidente real (`O1_INCIDENTE_CAMPO`) o una NC real (`O2_NC_DETECTADA`), además de dos orígenes sin dependencia (`O3_HALLAZGO_AUDITORIA`, `O4_REPORTE_EXTERNO`).

El frontend (`shc-controldoc`) es la fuente de verdad por encima de cualquier brief o contrato reconstruido cuando divergen (mismo criterio ya aplicado en `be-incidentes-catalogos` y `be-no-conformidades`). Para este cambio se leyó el código completo de `src/mocks/handlers/quality-events.handlers.ts` (1543 líneas), `qualityEvent.types.ts`, `qeOriginSync.ts`, todos los hooks reales de `features/quality-events/hooks/`, `qualityEventTransitions.ts`, `qualityEventPermissions.ts`, `qualityEventHelpers.ts`, todos los schemas Zod, y `plazoAjuste.constants.ts`/`.utils.ts` — no solo el contrato reconstruido ni el PRD. Cuatro preguntas genuinas (sin poder resolverse leyendo código, por tratarse de decisiones de producto/arquitectura) se escalaron a Toño vía `AskUserQuestion` y quedaron confirmadas 2026-08-20 (ver Decisions D5, D9, D14, D15).

## Goals / Non-Goals

**Goals:**
- Endpoints reales de Quality Events con paridad de comportamiento contra `quality-events.handlers.ts`, salvo en los puntos donde Toño confirmó explícitamente una implementación más estricta que el mock (state machine, RN-QE-002/003/009, gating de delete/reactivar).
- Vinculación funcional de extremo a extremo entre QE y su Incidente/NC de origen — incluye ampliar dos comandos backend ya existentes (`ActualizarInvestigacion` de Incidentes, `ActualizarNoConformidad` de NC) y agregar `Incidente.QeId`.
- Mantener el patrón CQRS ya establecido, reutilizando `EmpresaSecuencia` y el patrón de audit trail append-only, sin reinventar ningún mecanismo.

**Non-Goals:**
- Asistencia IA (5 Porqués/causa raíz/ACs sugeridas) — botón de UI sin integración backend.
- Generación real del PDF de exportación — el backend solo registra auditoría de `export-pdf`; el PDF lo arma `buildQualityEventPdf.ts` en el frontend.
- Envío real de notificaciones (push/email) — solo el hook no-op, mismo patrón que Incidentes/NC.
- Job automático de vencimiento de verificación (RN-QE-008, reapertura a los 10 días hábiles sin verificación) — requiere un scheduler que no existe. El endpoint dev-only `forzar-vencimiento-verificacion` sí se porta (ver D17), pero solo como utilidad manual gateada a `IsDevelopment()`.
- Backfill retroactivo de `qeId`/`qeGeneradoId` en Incidentes/NC creados antes de este cambio — quedan en `null` para siempre a menos que se re-vinculen manualmente.
- Validación del valor del PIN de firma contra una credencial real — no existe infraestructura de PIN en Auth todavía (ver D18).
- Autorización granular más allá de rol simple para acciones de QE (p.ej. verificar que el `auditorAsignadoId` de verificación de eficacia tenga permisos reales) — se replica la misma permisividad del mock en este punto.

## Decisions

### D1 — Estructura de Features
`Features/QualityEvents/{CrearQualityEvent,ListarQualityEvents,ObtenerQualityEvent,ActualizarQualityEvent,TransicionarEstadoQE,EliminarQualityEvent,ReactivarQualityEvent,CerrarQE,FirmarCierreQE,VerificacionEficaciaQE,EditarReporteInicialQE,EditarSeveridadQE,EditarMineralQE,ExportarPdfQE,ObtenerAuditTrailQE,SolicitarACEnQE,ListarAccionesCorrectivasQE,CrearAccionCorrectivaQE,ActualizarAccionCorrectivaQE,CambiarEstadoAccionCorrectivaQE,SolicitarAjustePlazoAC,RevisarAjustePlazoAC,ForzarVencimientoVerificacion}/`, cada uno con Command/Endpoint/Handler (+Validator donde aplique). `Features/QualityEvents/Shared/` para: generador de número (`QualityEventNumeroGenerator`), validador de transiciones (`QualityEventTransitionValidator`, puerto server-side de `VALID_QE_TRANSITIONS`), calculadora de plazos de AC (`AjustePlazoCalculator`, puerto de `plazoAjuste.utils.ts`), notificador no-op (`IQualityEventNotificationSender`/`NoOpQualityEventNotificationSender`, un solo servicio con varios métodos dado el mayor número de disparadores).

### D2 — Entidades de dominio
`QualityEvent` (con `AccionesCorrectivas` como colección propia `AccionCorrectivaQE`, FK `QualityEventId`), `AccionCorrectivaQE` (con `SolicitudesAjustePlazo` como colección propia `SolicitudAjustePlazoAC`, FK `AccionCorrectivaQEId`), `QualityEventAuditTrail` (append-only, FK `QualityEventId`, mismos campos que `NoConformidadAuditTrail`/`IncidenteAuditTrail`). Tipos owned: `NormativaVinculada` (`Norma`, `Clausula`, `NormaOtraDetalle?`), `ReporteExternoRef` (`NombreCliente`, `FechaRecepcion`). No se agrega un tipo `Adjunto` — confirmado que `QualityEvent` real (`qualityEvent.types.ts`) no tiene ese campo pese a que `CLAUDE.md` lo documenta; se trata de una desactualización de `CLAUDE.md`, no de una feature real pendiente (no bloqueante, se reporta al final).

### D3 — Numeración `QE-YYYY-NNN`, por empresa, corrigiendo el año hardcodeado del mock
El mock (`handlers.ts:234`) usa el literal `"2026"` en vez de calcular el año real — un atajo de mock, no una regla de negocio. El backend usa `EmpresaSecuencia` con `Tipo = "QE"` y el año calendario efectivo (`DateTime.UtcNow.Year`), mismo upsert atómico (`INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`) ya usado por `IncidenteNumeroGenerator`/`NoConformidadNumeroGenerator`. A diferencia de NC (`NC-<DOM>-YYYY-NNN`, correlativo por empresa+dominio), QE no tiene una dimensión adicional — correlativo solo por `(EmpresaId, "QE", Año)`, igual patrón simple que Incidentes.

### D4 — Multi-tenancy 404-nunca-403
Todos los handlers de QE (y de sus acciones correctivas y solicitudes de ajuste de plazo, que heredan aislamiento del QE padre) filtran por `EmpresaId == empresaActivaId` antes de cualquier otra validación, respondiendo 404 ante cualquier recurso de otra empresa o inexistente. `EmpresaId` se fija únicamente desde la sesión en la creación, nunca desde el body.

### D5 — DELETE/reactivar con gating por estado (decisión de Toño, 2026-08-20 — corrige el mock)
El mock (`handlers.ts:339-409`) no valida nada en ninguno de los dos endpoints: `DELETE` no verifica `estado` ni si ya estaba eliminado, y `reactivar` fuerza `estado: 'ABIERTO'` incondicionalmente, incluso reactivando un QE `VERIFICADO`. Se escaló como pregunta genuina (no hay una regla de negocio documentada que la resuelva) y Toño confirmó replicar el mismo criterio de gating ya usado en Incidentes/NC: `DELETE /api/quality-events/:id` (soft-delete) solo permitido si `estado === 'ABIERTO'` y `deletedAt` no está ya definido (422 en cualquier otro caso); `PATCH /api/quality-events/:id/reactivar` solo permitido si `deletedAt` está definido (422 si no), y **no** fuerza `estado` a `ABIERTO` — el `estado` que tenía el QE al momento de eliminarse se conserva intacto.

### D6 — Path real es `/reactivar`, no `/restore`
Confirmado por `quality-events.handlers.ts` y `useReactivateQualityEvent.ts` — `PATCH /api/quality-events/:id/reactivar`, a diferencia del nombre `/restore` usado en Incidentes/NC. Se replica el nombre real del path (contrato del frontend), no el patrón de nombres de los otros dos módulos.

### D7 — Cierre de Acción Correctiva de QE: no existe una sub-ruta `/cerrar` dedicada
A diferencia de NC (`POST .../acciones-correctivas/:acId/cerrar`), el frontend de QE cierra una AC vía el `PATCH .../acciones-correctivas/:acId/status` genérico, enviando `{ estado: 'CERRADA', descripcionEvidencia, evidenciaUrl? }` (`useCerrarQEAccion.ts` llama al mismo endpoint que un cambio de estado normal, sin ruta propia). El backend implementa un único `CambiarEstadoAccionCorrectivaQE` (`PATCH .../acciones-correctivas/:acId/status`) que, cuando `estado` pasa a `CERRADA`, exige `descripcionEvidencia` no vacía (mismo criterio de "cierre requiere evidencia" que NC, solo que expresado como un caso dentro del endpoint genérico de status en vez de un endpoint dedicado) y fija `fechaCierre` con hora del servidor.

### D8 — RN-QE-014: ventana de 2h para editar el reporte inicial (distinta de "descripción no editable fuera de ABIERTO")
Confirmado: son dos reglas distintas. `PATCH /api/quality-events/:id/editar-reporte-inicial` — permitido solo si `estado === 'ABIERTO'` y han pasado menos de 2 horas desde `fechaHoraReporte`, y solo por `reportadoPorId === usuario.id` o un `SUPERVISOR` cuyo `areasAsignadas` incluya `qe.areaId`. Campos bloqueados (422 si el body los incluye): `numero, origen, tipo, fechaHoraReporte, reportadoPorId, severidad`. Campos editables por este endpoint: `descripcion, areaId, turno, fechaHoraEvento, mineralInvolucrado, incidenteId, ncId, hallazgoCodigo, normativaVinculada, reporteExternoRef` — es el único endpoint que permite corregir `incidenteId`/`ncId`/`hallazgoCodigo`/`normativaVinculada`/`reporteExternoRef` tras la creación. La regla separada "`descripcion` no editable fuera de `ABIERTO`" (mencionada en `CLAUDE.md`) se aplica al `PATCH /:id` genérico — ver D11.

### D9 — Vinculación cross-módulo QE↔Incidente/NC (decisión de Toño, 2026-08-20 — incluida en este mismo cambio)
`qeOriginSync.ts` confirma que la creación desde origen O1/O2 es un flujo manual de dos pasos orquestado por el cliente, **nunca automático**: (1) `POST /api/quality-events` crea el QE con `incidenteId`/`ncId` tomados literalmente del body; (2) tras el éxito, el frontend (`QualityEventForm.tsx`) dispara por separado un `PATCH` sobre el Incidente/NC de origen (`{ qeId }` / `{ qeGeneradoId }`) para escribir el vínculo inverso. **Esto confirma que `CrearIncidenteHandler`/`CrearNoConformidadHandler` no se tocan** — la vinculación es enteramente responsabilidad de QE + los PATCH ya existentes de Incidentes/NC.

Se escaló como pregunta genuina si esto debía ir en este cambio o en uno separado (afecta a dos módulos ya archivados/aprobados) — Toño confirmó incluirlo aquí, porque sin esto la vinculación no persistiría de extremo a extremo aunque QE ya exista. Esto requiere:
1. Migración nueva `AddIncidenteQeId`: agrega `Incidente.QeId` (Guid?, nullable, sin FK enforcement — mismo criterio que `Incidente.AreaId`).
2. Ampliar `ActualizarInvestigacionCommand` (Incidentes) para aceptar `QeId` en el whitelist de campos editables.
3. Ampliar `ActualizarNoConformidadCommand` (NC) para aceptar `QeGeneradoId` (el campo ya existe en la entidad `NoConformidad` desde `be-no-conformidades`, solo estaba excluido del whitelist de PATCH por ser "server-only" en ese momento, cuando QE no existía).
4. `POST /api/quality-events` valida que el `incidenteId`/`ncId` enviado exista y pertenezca a la empresa activa (422 si no) — a diferencia del mock, que no valida existencia más allá de un lookup en el store en memoria. También valida que el Incidente/NC no esté ya vinculado a otro QE (`Incidente.QeId`/`NoConformidad.QeGeneradoId` ya seteado → 422), replicando esa parte sí presente en el mock (`handlers.ts:205-231`).

### D10 — `ORIGIN_REQUIRED_FIELD` por origen, replicado tal cual
Al crear un QE, el campo requerido según `origen` es: `O1_INCIDENTE_CAMPO` → `incidenteId`, `O2_NC_DETECTADA` → `ncId`, `O3_HALLAZGO_AUDITORIA` → `hallazgoCodigo`, `O4_REPORTE_EXTERNO` → `reporteExternoRef`. Validación 400 si el campo requerido por el origen enviado está ausente.

### D11 — RN-QE-002 con la validación estricta, no la del mock (decisión de Toño, 2026-08-20)
El mock (`handlers.ts:300-305`) solo verifica `causaRaizFirmadaEn` para bloquear `ANALISIS_COMPLETADO → EN_EJECUCION`, sin revisar que `causaRaizDefinitiva` no esté vacío — pese a que existe una función más estricta (`validateTransitionToEnEjecucion`, `qualityEventPermissions.ts:162-173`) que sí revisa ambos campos, nunca invocada por ningún handler. Se escaló junto con D14 (rigor general de máquina de estados) y Toño confirmó implementar la versión estricta: el backend bloquea la transición con 422 y mensaje legible ("RN-QE-002: ...") si `causaRaizDefinitiva` está vacío O `causaRaizFirmadaEn` no está seteado. El `PATCH /:id` genérico no permite editar `estado` (ya excluido de `QualityEventUpdateInput`) ni tiene ningún gate de estado sobre `descripcion` u otros campos en el mock — el backend SÍ aplica el invariante de `CLAUDE.md` ("`descripcion` no editable fuera de `ABIERTO`") como una validación explícita en `ActualizarQualityEvent`: si el body incluye `descripcion` y `estado !== 'ABIERTO'`, 422. Esto es una mejora deliberada sobre el mock (que no lo valida en absoluto), consistente con el criterio ya aplicado en D4 de `be-incidentes-catalogos`/D4 de `be-no-conformidades` ("nunca confiar en el cliente para lo que el servidor puede/debe garantizar").

### D12 — RN-QE-003: cierre bloqueado si alguna AC no está `CERRADA` con evidencia (server-side real, no solo emergente)
El mock no tiene un gate explícito en `/cerrar` — la transición a `PENDIENTE_CIERRE` es solo una consecuencia emergente del handler de status de AC (`handlers.ts:639-658`, auto-transiciona `EN_EJECUCION → PENDIENTE_CIERRE` cuando todas las ACs quedan `CERRADA` con evidencia), pero nada impide llamar `PATCH /:id/cerrar` directamente sin pasar por ahí. El backend valida explícitamente en `CerrarQE`: 422 si existe alguna `AccionCorrectivaQE` con `Estado !== 'CERRADA'` o sin `DescripcionEvidencia`, replicando la función ya construida pero no invocada `validateTransitionToPendienteCierre` (`qualityEventPermissions.ts:175-191`).

### D13 — RN-QE-009: `solicitudesAC > 0` bloquea `EN_INVESTIGACION → ANALISIS_COMPLETADO`
El mock incrementa `solicitudesAC` en `PATCH .../solicitar-ac` (`handlers.ts:1332-1350`) pero nunca lo lee de vuelta como gate — no existe ninguna función de referencia en el frontend para esta regla específica (a diferencia de D11/D12), así que es lógica nueva construida desde la regla de negocio documentada en `CLAUDE.md`/PRD, no un puerto de código existente. El backend bloquea con 422 la transición `EN_INVESTIGACION → ANALISIS_COMPLETADO` si `SolicitudesAC > 0`.

### D14 — Máquina de estados server-side real (`VALID_QE_TRANSITIONS`) (decisión de Toño, 2026-08-20)
El mock no valida secuencia alguna en `PATCH /:id/status` — acepta cualquier `nuevoEstado` salvo los dos checks puntuales de D11 y de firma de cierre. Se escaló junto con D11/D12/D13 como una única pregunta de rigor general (a diferencia de NC, donde la permisividad del mock se replicó tal cual por no existir lógica de referencia más estricta ya construida): aquí sí existe, completa y probada en el frontend (`qualityEventTransitions.ts`), simplemente nunca conectada a ningún handler. Toño confirmó portarla: `TransicionarEstadoQE` valida que `(estadoActual, nuevoEstado)` sea una transición válida según el mismo mapa (`ABIERTO→[EN_INVESTIGACION]`, `EN_INVESTIGACION→[ANALISIS_COMPLETADO]`, `ANALISIS_COMPLETADO→[EN_EJECUCION]`, `EN_EJECUCION→[PENDIENTE_CIERRE]`, `PENDIENTE_CIERRE→[CERRADO]`, `CERRADO→[EN_VERIFICACION]`, `EN_VERIFICACION→[VERIFICADO, EN_INVESTIGACION]` — la reapertura, ver D16 —, `VERIFICADO→[]`), 422 si no. `REABIERTO` no es un valor válido de `estado` en ningún momento (ver D16), confirmando que ni siquiera aparece como destino en el mapa server-side.

### D15 — RN-QE-004 reconciliada como regla superada por el modelo de un rol por usuario (decisión de Toño, 2026-08-20)
El frontend retiró explícitamente (2026-07-17, comentario en código) la rama "mismo firmante Jefe Calidad y Supervisor → escala a `ALTA_DIRECCION`" por ser estructuralmente inalcanzable: `User.rol` es un único valor, ningún usuario real puede ser simultáneamente `JEFE_CALIDAD_SYST` y `SUPERVISOR` del área. `resolveRolSegundaFirma` siempre devuelve `'SUPERVISOR'`. Se escaló como pregunta genuina (contradice el texto literal de `CLAUDE.md`) y Toño confirmó reconciliar la regla como superada, mismo patrón ya aplicado a RN-INC-006 vs. PRD §3 y a RN-NC-003 en `be-no-conformidades` D7: el backend replica `ResolverRolSegundaFirma` devolviendo siempre `SUPERVISOR`, sin implementar la rama de escalada a Gerencia. Si en el futuro el modelo de roles cambia (multi-rol por usuario), esta reconciliación deberá revisarse.

### D16 — RN-QE-005: notificación de severidad urgente — hook en creación (nuevo) + hooks existentes en cierre/verificación (replicados)
El mock nunca notifica en la creación (pese a que `CLAUDE.md` documenta "severidad CRITICA → notificar a Gerencia en <2 minutos" como si aplicara a cualquier momento). Sí notifica — con criterio `severidad === 'ALTA' || 'CRITICA'`, más amplio que solo `CRITICA` — en `firmar-cierre` (segunda firma) y en `verificacion-eficacia` con resultado `EFECTIVO` (`handlers.ts:1092-1107`, `1271-1286`). `editar-severidad` calcula `requiereNotificacionUrgente` pero solo lo devuelve en la respuesta, sin notificar. El backend agrega un hook best-effort no-op en `CrearQualityEvent` cuando `severidad === 'CRITICA'` (paridad con el invariante documentado, mismo precedente que D5 de `be-no-conformidades` con RN-NC-002), y replica los dos hooks existentes de cierre/verificación con el mismo criterio `ALTA || CRITICA`. `editar-severidad` también invoca el hook cuando la nueva severidad es `CRITICA` (coherente con calcular pero no ignorar `requiereNotificacionUrgente`).

### D17 — Reapertura: dos rutas, mismo target `EN_INVESTIGACION`, incrementan `ciclo`
Confirmado (`handlers.ts:1166-1203` reapertura por vencimiento, `1291-1329` reapertura por verificación `NO_EFECTIVO`): ambas fijan `estado: 'EN_INVESTIGACION'` directamente (nunca pasan por un estado persistido `REABIERTO`) e incrementan `ciclo`, agregando una entrada de audit trail con `accion: 'REABIERTO'` usada solo como etiqueta de motivo (`campoModificado: 'motivo'`, `valorNuevo: 'VENCIMIENTO_PLAZO'` o `'NO_EFECTIVO'`). El backend replica ambos disparadores: `VerificacionEficaciaQE` con `resultado: 'NO_EFECTIVO'` reabre automáticamente; `ForzarVencimientoVerificacion` (dev-only, ver siguiente decisión) también reabre. El job automático real de vencimiento a los 10 días hábiles (RN-QE-008) queda fuera de alcance (Non-Goals) por requerir un scheduler inexistente.

### D18 — `forzar-vencimiento-verificacion` portado como utilidad dev-only
El propio contrato original lo marcaba "probablemente no debe existir en producción". Se decide portarlo gateado a `IsDevelopment()` (mismo patrón que el dev seed de Incidentes/NC), sin exponerlo en ningún flujo de producción — permite probar manualmente la reapertura por vencimiento sin esperar 10 días hábiles reales ni construir un scheduler. Body `{ auditorAsignadoId? }`, mismo shape que el mock. Esta decisión no se escaló a `AskUserQuestion` por ser de bajo riesgo y reversible (una utilidad de desarrollo, no una regla de negocio de producción); se deja explícita aquí para que Toño la revise en el reporte final igual que cualquier otra decisión.

### D19 — PIN de firma: solo validación de formato, sin credencial real (gap conocido, replicado del mock)
Ni el mock ni el backend de Auth actual tienen infraestructura de PIN por usuario — `firmar-cierre` valida que `pin` sea un string de 4 dígitos (Zod) pero no lo compara contra ningún valor almacenado, en el mock ni en este backend. Se documenta como gap conocido, no como regresión introducida por este cambio: no existe ningún lugar en el sistema (mock o real) donde un PIN se registre o valide de verdad. Fuera de alcance construir esa infraestructura aquí.

### D20 — Filtros de listado: `soloReincidencias` sí, `ciclo` crudo no
El tipo `QEListParams` del frontend expone un parámetro `ciclo`, pero el handler del mock nunca lo lee — es un campo muerto. El filtro real y usado es `soloReincidencias` (booleano, `ciclo > 1`). El backend implementa `soloReincidencias` como `WHERE ciclo > 1` en `ListarQualityEvents` y no implementa un filtro `ciclo` crudo, replicando lo que el frontend realmente consume.

### D21 — Dev seed
No se requiere seed nuevo de catálogos. Sin datos de desarrollo propios de Quality Events en este cambio — mismo criterio que Incidentes/NC: la app arranca sin QEs, se crean vía UI/API.

## Risks / Trade-offs

- [Riesgo] D9 (vinculación cross-módulo) modifica dos comandos backend ya archivados/aprobados (`ActualizarInvestigacion`, `ActualizarNoConformidad`) → Mitigación: cambio aditivo puro (amplía whitelist, no modifica comportamiento existente de ningún otro campo); se agregan tests de regresión sobre ambos comandos además de los nuevos de QE.
- [Riesgo] D11/D12/D13/D14 (máquina de estados y validaciones estrictas) hacen que este backend sea deliberadamente más estricto que el mock activo — un frontend que hoy depende de la permisividad del mock (p.ej. saltar directo de estado sin pasar validaciones) podría romperse contra el backend real → Mitigación: todas las transiciones válidas documentadas en `qualityEventTransitions.ts` son exactamente las que el frontend real ya usa (botones de UI ya respetan ese mapa); solo se endurece la ruta de API directa, que el frontend no explota hoy. Documentado explícitamente para que la verificación manual (tasks.md) incluya una pasada end-to-end del flujo completo de UI, no solo tests de integración aislados.
- [Riesgo] D15 (RN-QE-004 reconciliada) deja sin implementar una regla de negocio literal de `CLAUDE.md` → Mitigación: mismo patrón ya aceptado para RN-INC-006/RN-NC-003; si el modelo de roles cambia a multi-rol en el futuro, es una revisión de código acotada (un método), no un rediseño.
- [Riesgo] D16 (hook de notificación en creación) es lógica nueva sin contraparte en el mock → Mitigación: mismo criterio ya usado en D5 de `be-no-conformidades` (RN-NC-002) — hook best-effort, no bloqueante, con TODO explícito; no afecta el código de respuesta si falla.
- [Riesgo] Discrepancia de `CLAUDE.md` sobre el campo `adjuntos` (documentado, no existe en código real) → Mitigación: señalado en el reporte final como corrección de documentación pendiente, no bloqueante para este cambio.

## Migration Plan

1. Migración EF Core nueva: `AddQualityEvents` (`quality_events`, `acciones_correctivas_qe`, `solicitudes_ajuste_plazo_ac`, `quality_event_audit_trail`).
2. Migración EF Core adicional: `AddIncidenteQeId` (columna nullable `qe_id` en `incidentes`, sin FK enforcement).
3. Aplicar ambas migraciones (`dotnet ef database update`) antes de probar los endpoints nuevos.
4. Sin dev seed adicional — no hay filas de `empresa_secuencias` de tipo `QE` hasta la primera creación real.
5. Sin rollback especial más allá de revertir ambas migraciones — no hay datos de producción todavía.

## Open Questions

Las preguntas genuinas del brief original (gating de delete/reactivar, alcance cross-módulo, rigor de máquina de estados, reconciliación RN-QE-004) se resolvieron con `AskUserQuestion` antes de escribir este documento y ya están incorporadas como decisiones confirmadas (D5, D9, D14, D15) — no quedan abiertas.
