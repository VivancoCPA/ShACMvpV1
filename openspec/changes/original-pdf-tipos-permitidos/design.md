## Context

El flujo real de archivo original (confirmado leyendo el código, no el PRD) es:

1. **Creación:** `POST /api/documents` (`CrearDocumentoHandler`) crea el `Documento` solo con metadatos — nunca recibe archivo. El frontend, si el usuario seleccionó un archivo en el mismo formulario, hace una segunda llamada: `POST /api/documents/:id/archivo-original` (`ReemplazarArchivoOriginalHandler`, el mismo handler para la carga inicial y para reemplazos posteriores).
2. **Edición:** `PUT /api/documents/:id` (`EditarDocumentoHandler`) — **`Tipo` no es un campo de `EditarDocumentoCommand`**. El comentario en el propio archivo lo confirma: *"tipo/codigo NUNCA se editan ... 'tipo' está deliberadamente fuera de la lista `allowed`"*. El `<select id="tipo">` de `DocumentForm.tsx` no está deshabilitado en modo edición, pero cualquier valor que el usuario elija ahí se descarta silenciosamente al guardar — comportamiento preexistente, no introducido por este cambio.
3. **Firma/publicación:** `FirmarPublicarDocumentoHandler` siempre llama `IDocumentoPdfConverter.ConvertirAsync` sobre el original antes de `DocumentoPdfGenerator.SellarPublicado`.
4. **Visor:** `VisualizarDocumentoHandler.ObtenerVistaPreviaAsync` hace lo mismo antes de `SellarVistaPrevia`, con caché por clave derivada del nombre de archivo ya archivado.
5. **Nueva versión:** `NuevaVersionDocumentoHandler` + `DocumentoStorageService.CopiarOriginalAsync` copian el archivo tal cual, sin ninguna lógica dependiente del tipo de archivo — ya son agnósticos.
6. Ningún endpoint de escritura (`CrearDocumento`, `EditarDocumento`, `ReemplazarArchivoOriginal`) valida hoy la extensión o el contenido del archivo subido. La única restricción existente es client-side, en `FileUploadField.tsx` (`ACCEPTED_TYPES_ORIGINAL = {docx, xlsx}`, atributo `accept=".docx,.xlsx"`).

**Nota técnica — divergencia con las instrucciones de origen (2026-10-13):** el documento de instrucciones que motivó este change describe un punto de validación "cambio de tipo con un PDF ya cargado" en edición. Leyendo `EditarDocumentoCommand`/`EditarDocumentoHandler` reales, `Tipo` es inmutable después de la creación — no existe tal escenario en el backend. La validación equivalente solo tiene sentido **dentro del formulario de creación**, en memoria, antes de la primera persistencia (el usuario elige `tipo` y adjunta un archivo en la misma pantalla, ambos aún no guardados). Este design.md documenta esa divergencia en vez de resolverla forzando un caso de borde que no puede ocurrir contra el backend real.

**Nota técnica — drift de specs preexistente:** `openspec/specs/document-file-upload/spec.md`, `document-form/spec.md` y `document-schemas/spec.md` describen una versión más antigua del código (un único `accept` genérico sin variantes, `PATCH` en vez de `PUT` para editar, `createDocument.schema.ts`/`updateDocument.schema.ts` que ya no existen — todo quedó consolidado en `documentForm.schema.ts`). Este change no corrige ese drift retroactivamente; los requirements nuevos que agrega se escriben para no contradecir el texto ya desactualizado, y quedan acotados al comportamiento nuevo.

## Goals / Non-Goals

**Goals:**
- Permitir subir un PDF nativo como archivo original para documentos `INF`, `MAT` y `PLAN`, publicándolo sin pasar por LibreOffice.
- Cerrar la brecha real de validación de formato en el servidor (hoy inexistente) para todo tipo de documento, no solo para los que aceptan PDF.
- Evitar que un PDF nativo protegido/corrupto termine "publicado" sin sello y sin que nadie lo note.
- Mantener un único punto de verdad por capa para "qué tipos aceptan PDF" (espejo backend/frontend, patrón ya usado por `DocumentoAsignacionRoles`/`DOCUMENT_ASIGNACION_ELIGIBLE_ROLES`).

**Non-Goals:**
- No se habilita la carga manual del "PDF de distribución" (sigue siendo exclusivamente generado por el sistema al firmar) — opción B del documento de origen, descartada explícitamente por Toño.
- No se corrige el drift de specs preexistente en `document-file-upload`/`document-form`/`document-schemas` más allá de lo necesario para este feature.
- No se deshabilita el `<select id="tipo">` en modo edición (bug preexistente de UX sin efecto funcional real, fuera de alcance de este change).
- No se reescribe el mecanismo de degradación ya aceptado para `SellarPublicado`/`SellarVistaPrevia` cuando el PDF de entrada viene de una conversión LibreOffice exitosa pero PdfSharpCore no logra abrirlo — ese caso sigue degradando a "sin sello" tal como hoy. Solo se agrega un camino distinto, más estricto, específico para cuando el PDF de entrada es el original nativo subido por el usuario (ver Decisión D4).

## Decisions

**D1 — Fuente única de tipos permitidos.** `DocumentoFormatosPermitidos` (nueva clase estática en `Features/Documentos/Shared/`, mismo namespace y estilo que `DocumentoAsignacionRoles`) expone `TiposConOriginalPdf = [DocType.INF, DocType.MAT, DocType.PLAN]` y un método `EsFormatoPermitido(DocType tipo, string extension, byte[] primerosBytes)`. El espejo frontend es `TIPOS_CON_ORIGINAL_PDF` en `features/documents/constants.ts`, con el mismo comentario de "espejo de X.cs — el servidor es quien la aplica de verdad" que ya usa `DOCUMENT_ASIGNACION_ELIGIBLE_ROLES`.

**D2 — Validación de extensión + firma binaria, no solo Content-Type.** El `Content-Type` del `IFormFile` lo fija el cliente y no es confiable. `DocumentoFormatosPermitidos` valida (a) la extensión del nombre de archivo y (b) los primeros bytes: PDF empieza con los 5 bytes ASCII `%PDF-`; `.docx`/`.xlsx` son ZIP y empiezan con `PK\x03\x04` (o las variantes `PK\x05\x06`/`PK\x07\x08` de ZIP vacío/spanned, poco probables pero correctas de aceptar). Un archivo que pasa la extensión pero no la firma (`.pdf` renombrado desde un `.txt`, o un `.docx` renombrado a `.pdf`) se rechaza igual. Esto se aplica en `ReemplazarArchivoOriginalHandler` — único punto de entrada real del archivo original, tanto en la carga inicial post-creación como en reemplazos — leyendo los primeros bytes del `IFormFile.OpenReadStream()` sin materializar el archivo completo en memoria.

**D3 — Dónde vive la validación de "cambio de tipo con PDF ya cargado".** Dado que `Tipo` es inmutable tras la creación (ver Context), esta validación es exclusivamente client-side: `documentFormSchema.superRefine` (ya existente, se le agrega una rama) rechaza la combinación `archivoOriginalFile` cuyo `type`/nombre no matchea `tipo` actual, usando el mismo `TIPOS_CON_ORIGINAL_PDF`. Esto cubre tanto "el usuario sube un PDF y luego cambia tipo a PRC" como el orden inverso, porque `superRefine` revalida sobre el estado completo del formulario en cada submit/cambio relevante (React Hook Form + `zodResolver`). No se agrega ninguna validación de "tipo cambiado" en `EditarDocumentoHandler`/`EditarDocumentoCommand` porque no hay tipo que cambiar ahí.

**D4 — PDF nativo protegido/dañado: error de negocio explícito, no degradación silenciosa.** Hoy, si `PdfSharpCore.PdfReader.Open` falla dentro de `SellarPublicado`/`SellarVistaPrevia`, el handler llamante atrapa la excepción y sirve `pdfConvertido` (el PDF de entrada) sin sello — aceptado porque ese PDF de entrada siempre viene de una conversión LibreOffice exitosa (un PDF bien formado, el fallo es un caso raro de incompatibilidad de PdfSharpCore con cierta salida de LibreOffice). Para un original PDF nativo, ese mismo código de entrada es el archivo que subió el usuario: si está protegido con contraseña o corrupto, "degradar sin sello" significaría publicar/previsualizar silenciosamente un archivo que el propio sistema no pudo abrir — inaceptable.
Por eso, para el camino de PDF nativo se agrega una validación temprana: al reemplazar el archivo original con un PDF nativo (`ReemplazarArchivoOriginalHandler`), el sistema intenta `PdfReader.Open` en modo lectura sobre los bytes recién subidos; si falla, rechaza la carga con `BadRequestBusinessException` ("El PDF está protegido o dañado; súbelo sin contraseña") — el usuario nunca llega a tener un original roto persistido. Como red de seguridad (seeds/migraciones u otro flujo que lo deje pasar), `FirmarPublicarDocumentoHandler`/`VisualizarDocumentoHandler` distinguen explícitamente "original es PDF nativo" de "original convertido por LibreOffice": si el `PdfReader.Open` falla sobre un original nativo, lanzan `BusinessRuleException("PDF_PROTEGIDO_O_DANADO")` en vez de degradar; el camino de conversión LibreOffice conserva el fallback existente sin cambios.

**D5 — Punto único de la decisión "¿convertir o no?".** Se encapsula en un helper `ObtenerPdfBaseAsync(rutaOriginal, nombreOriginal, ct)` en `Features/Documentos/Shared/` (usado por `FirmarPublicarDocumentoHandler` y `VisualizarDocumentoHandler.ObtenerVistaPreviaAsync`): si la extensión del original es `.pdf`, lee y valida los bytes directamente (D4); si no, delega a `IDocumentoPdfConverter.ConvertirAsync` (comportamiento actual, sin cambios). Ningún handler vuelve a decidir "es PDF" por su cuenta en más de un lugar.

**D6 — MSW replica la misma regla, no la reinventa.** El handler MSW de `POST /api/documents/:id/archivo-original` importa `TIPOS_CON_ORIGINAL_PDF` de `constants.ts` (mismo patrón que `documents.handlers.ts` ya hace con `DOCUMENT_ASIGNACION_ELIGIBLE_ROLES`) y responde `400` si el tipo de archivo no es compatible — sin duplicar la lista.

**Nota técnica (D6, descubierta al implementar):** el plan original era validar por extensión del nombre de archivo. En la práctica (confirmado con un test aislado), el nombre original del `File` no sobrevive el viaje de ida y vuelta por `request.formData()` en el entorno MSW/jsdom usado por los tests (axios → XHR interceptado por MSW en Node → `request.formData()` reconstruye el archivo como un `Blob` genérico con `name: "blob"`), aunque el `type` (MIME) sí se preserva correctamente. Por eso el handler MSW valida por `file.type`, no por extensión — exactamente el mismo criterio que ya usa `FileUploadField.tsx` en el cliente (`ACCEPTED_TYPES_ORIGINAL` es un `Set` de MIME types). Esto es una limitación del entorno de test/mock (Node), no necesariamente del navegador real; de cualquier forma, MIME type es la señal más estable disponible en ambos casos y es la que ya usa el resto del código cliente, así que no hay pérdida de cobertura real.

**Nota técnica adicional (bug preexistente descubierto, corregido como parte de este change):** `documents.api.ts#replaceArchivoOriginal` y los dos `POST .../archivo-original` inline de `useDocumentForm.ts` fijaban `headers: { 'Content-Type': 'multipart/form-data' }` a mano, sin el `boundary` que un multipart real necesita — axios nunca llegaba a calcular el boundary real porque el header ya estaba "fijado". Esto era inofensivo mientras el handler MSW ignoraba el body (comentario preexistente, ahora falso: "MSW cannot parse multipart/form-data boundaries"), pero rompía cualquier intento real de leer el archivo subido — exactamente lo que este change necesita hacer. Se corrigió a `{ 'Content-Type': undefined }`, el mismo patrón ya documentado en `locales.api.ts` (`MULTIPART_CONFIG`) para que axios calcule el boundary real a partir del `FormData`.

## Risks / Trade-offs

- **[Riesgo] Verificar la firma binaria de un ZIP válido es más laxo que validar que sea específicamente OOXML (`.docx`/`.xlsx`) y no cualquier otro ZIP renombrado.** → Mitigación: alcance explícitamente acotado a lo que pide el documento de origen (`PK` + extensión); una validación OOXML completa (abrir el ZIP y verificar `[Content_Types].xml`) queda fuera de alcance — anotar como posible mejora futura, no bloquea esta implementación.
- **[Riesgo] Leer los primeros bytes de un `IFormFile` dos veces (validación + guardado) podría fallar si el stream no es seekable.** → Mitigación: `IFormFile.OpenReadStream()` sobre un archivo de formulario ASP.NET Core siempre es seekable (respaldado en memoria o en un archivo temporal según tamaño) — se verifica con un test que sube un archivo por encima del umbral de buffering en memoria de Kestrel.
- **[Riesgo] El check `PdfReader.Open` en modo lectura durante la carga agrega latencia/CPU en el endpoint de subida.** → Mitigación: solo se ejecuta cuando la extensión es `.pdf` y el tipo del documento admite PDF (nunca para `.docx`/`.xlsx`); el documento de origen pide exactamente esta detección temprana.
- **[Trade-off] El `<select id="tipo">` sigue sin deshabilitarse visualmente en edición**, aunque ya no tiene ningún efecto (ni antes ni después de este change). Se documenta como Non-Goal en vez de expandir el alcance del change.

## Migration Plan

- Sin migración de datos: no se reinterpretan documentos existentes, solo se amplía qué formatos son aceptados para `INF`/`MAT`/`PLAN` desde ahora.
- Despliegue en un solo paso (backend + frontend + MSW juntos, mismo contrato de API) — un frontend viejo contra un backend nuevo simplemente sigue sin ofrecer `.pdf` en el `accept` del input, sin romper nada; un backend viejo contra un frontend nuevo rechazaría el PDF únicamente por el `accept` del navegador (ningún frontend real salta esa validación), así que no hay ventana de incompatibilidad real que proteger con flags.
- Rollback: revertir el commit/PR es suficiente: no hay cambio de esquema de base de datos ni de contrato de API.

## Open Questions

- Ninguna pendiente de decisión humana — Toño ya resolvió D1 (opción A, sin carga manual del PDF de distribución) y D2 (solo `INF`/`MAT`/`PLAN`) en la conversación de origen (2026-10-13).
