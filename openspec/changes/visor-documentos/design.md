## Context

Hoy, revisar el contenido real de un documento (`.docx`/`.xlsx`) requiere descargarlo. El backend .NET (`ShcMvpEndPoint`) ya reemplazó al mock para M1 (`be-documentos-api`, archivado) y ya tiene:

- `IDocumentoPdfConverter` / `LibreOfficePdfConverter` (`Features/Documentos/Shared/`) — conversión real `.docx`/`.xlsx` → PDF vía LibreOffice headless, con aislamiento por conversión, límite de concurrencia global (`MaxConcurrentConversions`) y `PdfConversionException` en fallos. Usado hoy solo por `FirmarPublicarDocumentoHandler`.
- `DocumentoPdfGenerator` (estático, PdfSharpCore) — **solo 2 métodos hoy**: `SellarPublicado` (sello de publicación en cada página) y `GenerarControlado` (marca de agua "COPIA NO CONTROLADA" + hash, usado por `ExportarPdfControladoHandler`, RN-DOC-007). **No existe ningún método de sellado para "VISTA PREVIA" ni para "OBSOLETO"** — se verificó por búsqueda en el código: ambas marcas son trabajo nuevo, no reutilización.
- `DocumentoStorageService` — guarda originales y PDFs de distribución bajo `wwwroot/uploads/documentos/{empresaId}/{documentoId}/{original|distribucion}/...`, servidos sin autenticación por `app.UseStaticFiles()` (confirmado en `Program.cs`, llamado antes de `UseAuthentication()`). **Hallazgo de seguridad ya conocido, no se resuelve en este change** (ver sección propia más abajo).
- `DocumentPermissionResolver` — `DocRole { AUTOR, REVISOR, APROBADOR, JEFE_CALIDAD, OPERARIO }`, matriz real de 6 estados × 5 roles con 9 flags base + 3 flags derivados (`CanViewArchivoOriginal`, `CanReplaceArchivoOriginal`, `CanViewArchivoDistribucion`), más un gate aparte `CanViewArchivoOriginalConCA34` (más permisivo, usado solo por el endpoint de archivo original) y `CanAccessByConfidencialidad`.
- Un flujo de "ver archivo" ya existente, **que no es un visor embebido**: `GET /:id/archivo` (`ObtenerArchivoHandler` + `DocumentoArchivoVigenteResolver`) resuelve el archivo vigente (distribución si `PUBLICADO`/`EN_REVISION_PERIODICA`, si no el original sujeto a `CanViewArchivoOriginalConCA34`), emite un token firmado HMAC con TTL de 15 min (`DocumentoSignedUrlService`), registra `VISUALIZACION`, y devuelve `{ url: "/api/documents/stream/{token}", ... }`. `GET /api/documents/stream/{token}` (`StreamArchivoEndpoint`) sirve el archivo **sin `.RequireAuthorization()`** a propósito — el token reemplaza al JWT para permitir `window.open()` en pestaña nueva sin adjuntar el Bearer token. El frontend (`useGetArchivoUrl` → botón "Ver archivo") usa esto hoy para abrir el archivo en una pestaña nueva, nunca embebido.
- El modal "pdf.previewTitle" en `DocumentActionPanel` **no es un visor de PDF** — es una tarjeta HTML cosmética (código, título, área, vigencia, aprobador, leyenda) que solo confirma antes de disparar `POST /exportar-pdf` (descarga real vía Blob). Convive sin tocarse con el visor nuevo; no se unifica (ver Decisión D7).

## Goals / Non-Goals

**Goals:**
- Visor de PDF embebido (pdf.js/`react-pdf`) para ver el contenido real del documento dentro de la app, sin descargar.
- Extender el acceso de vista a `EN_APROBACION` (el aprobador hoy no ve nada del contenido antes de firmar).
- Reutilizar la matriz de permisos real existente — ninguna regla de acceso nueva salvo la extensión explícita a `EN_APROBACION` (D2 del proposal) ya decidida por Toño.
- Cerrar, para este flujo, el `TODO` histórico de `document-pdf-security` sobre RN-DOC-010 ("generación server-side con marcas de agua reales y permisos restrictivos... deferred until the .NET backend exists") — el backend ya existe, este change es su primera implementación real.

**Non-Goals:**
- No reemplaza ni modifica `GET /:id/archivo` + `/stream/{token}` (ver Decisión D1) ni el modal cosmético de `exportar-pdf`.
- No resuelve el hallazgo de `wwwroot`/`UseStaticFiles()` sin autenticación — se documenta para un change aparte (`almacenamiento-documentos-privado`).
- No agrega comentarios/anotaciones al visor (D4 del proposal).
- No implementa un mecanismo de limpieza/expiración de la caché de vistas previas (ver D5) — solo invalidación lógica (archivos huérfanos, nunca borrados, mismo criterio que `DocumentoStorageService` con los originales reemplazados).

## Decisions

### D1 — El visor es un endpoint autenticado que devuelve bytes, no un token firmado sin auth
`GET /api/documents/{id}/visor` SHALL requerir `.RequireAuthorization()` y devolver los bytes del PDF directamente (`Results.File`/`Results.Bytes`, `Content-Disposition: inline`), siguiendo el mismo patrón que `archivo-original`/`archivo-distribucion` — **no** el patrón `archivo` + `stream/{token}`.

Razón: ese patrón existe específicamente para que `window.open(url)` abra el archivo en una pestaña nueva sin adjuntar el header `Authorization` (de ahí que `/stream/{token}` esté deliberadamente sin `[Authorize]`, con el token HMAC como sustituto). El visor embebido necesita lo opuesto: pdf.js consume el PDF vía `fetch`/axios con el JWT adjunto (instrucción explícita: "Cargar el PDF con la instancia `api` (axios con JWT) como blob; nunca apuntar el visor a una URL estática"), para que cada apertura quede sujeta al mismo chequeo de permisos por request, sin un token reusable de 15 minutos flotando en el DOM/historial del navegador. Los dos mecanismos coexisten sin tocarse.

### D2 — Permiso del visor = `CanRead` de la matriz real, con una excepción documentada para OBSOLETO
El visor SHALL exponer contenido cuando `DocumentPermissionResolver.GetBasePermissions(estado, docRole).CanRead` es `true` — sin inventar un flag nuevo, reutilizando exactamente la matriz de `document-permissions`/`DocumentPermissionResolver`.

**Excepción explícita para `OBSOLETO`** (la tabla del documento de instrucciones dice "según la matriz de OBSOLETO, incluida la excepción CA-34"): el gate real SHALL ser `CanRead || DocumentPermissionResolver.CanViewArchivoOriginalConCA34(estado, docRole, actorRolGlobal)`. Esto es necesario porque `CanViewArchivoOriginalConCA34` ignora el `docRole` resuelto (no es un `OR` sobre la matriz base, es un chequeo independiente por rol global `JEFE_CONTROL_DOCUMENTARIO`/`ALTA_DIRECCION`) — sin este `OR` explícito, un `ALTA_DIRECCION` o `JEFE_CONTROL_DOCUMENTARIO` cuyo `docRole` resuelva a `AUTOR` (ambos tienen `CanRead: false` en `OBSOLETO` según la matriz base) quedaría bloqueado del visor pese a tener acceso histórico reconocido al archivo original del mismo documento — una inconsistencia que el documento de instrucciones pedía señalar si no encajaba con la matriz real; esta es esa señal, resuelta explícitamente aquí en vez de dejarla abierta.

Para los otros 5 estados, `CanRead` solo (sin CA-34) es suficiente y coincide 1:1 con la tabla del proposal.

### D3 — Qué contenido sirve el endpoint por estado (reutilizando lo que ya existe)
- `BORRADOR` / `EN_REVISION` / `EN_APROBACION`: vista previa generada desde `ArchivoOriginalUrl` vía `IDocumentoPdfConverter.ConvertirAsync` (igual que `FirmarPublicarDocumentoHandler`), sellada con el nuevo método `DocumentoPdfGenerator.SellarVistaPrevia(pdfConvertido, documento)` → marca "VISTA PREVIA — NO CONTROLADO — {ESTADO}" en cada página. **Cacheada** (ver D5) — es la única rama costosa (invoca LibreOffice).
- `PUBLICADO` / `EN_REVISION_PERIODICA`: sirve `ArchivoDistribucionUrl` tal cual desde disco, sin regenerar — mismo criterio que `ArchivoDistribucionHandler` ("SHALL NOT regenerar el PDF en cada solicitud"). Sin caché adicional: ya es un archivo en disco.
- `OBSOLETO`: lee `ArchivoDistribucionUrl` desde disco y aplica al vuelo el nuevo método `DocumentoPdfGenerator.SellarObsoleto(pdfDistribucion)` → encabezado "OBSOLETO — No usar" en rojo en cada página. Sin caché: es un sellado barato (PdfSharpCore sobre un PDF ya chico, sin conversión LibreOffice) y así nunca hay que invalidar nada cuando — hipotéticamente — cambiara el estado de nuevo (no puede, `OBSOLETO` no tiene transiciones salientes, pero mantiene el código más simple no cachear algo que no lo necesita).
- Si no hay `ArchivoOriginalUrl` (estados 1) ni `ArchivoDistribucionUrl` (estados 2-3): `404` con mensaje "Este documento aún no tiene archivo para visualizar" (mismo texto que pide el documento de instrucciones).
- Si la conversión falla: mismo patrón que la firma — `BusinessRuleException` con código `PDF_CONVERSION_FAILED`, nunca `500`, con `logger.LogError` del detalle técnico (reutilizando el fix de `fix-log-conversion-pdf`, que hoy solo registra éxitos).

### D4 — Caché de vista previa: ubicación, clave y ciclo de vida
No existe ningún mecanismo de caché de archivos hoy (confirmado: `ReemplazarArchivoOriginalHandler` no tiene ningún gancho de invalidación) — esto es diseño nuevo, no una extensión de algo existente.

- **Ubicación**: `Path.Combine(env.ContentRootPath, "cache", "documentos-preview", empresaId, documentoId)` — explícitamente bajo `ContentRootPath`, no `WebRootPath`/`wwwroot`, para que `app.UseStaticFiles()` nunca pueda servirlo (ver hallazgo de seguridad). Un nuevo servicio `DocumentoPreviewCacheService` encapsula esta ruta (mismo espíritu que `DocumentoStorageService`, pero sin exponer un `Url` público — el contenido solo sale por el endpoint `/visor`, nunca por una ruta estática).
- **Clave de caché**: el nombre de archivo ya archivado de `ArchivoOriginalUrl` (`{yyyyMMddHHmmssfff}-{nombreOriginal}`, asignado por `DocumentoStorageService.GuardarOriginalAsync`) — ese nombre ya es único por cada reemplazo real del original (lo confirma el propio mecanismo de archivado con timestamp). El archivo de caché se guarda como `{documentoId}__{nombreArchivoOriginalArchivado}.pdf`.
- **Invalidación**: cuando `ReemplazarArchivoOriginalHandler` guarda un nuevo original, su nombre archivado (y por tanto la clave de caché) cambia automáticamente — la vista previa cacheada del original anterior queda huérfana (nunca se borra activamente, mismo criterio de "nunca destruir evidencia" que ya aplica a los originales reemplazados), y la próxima apertura del visor genera una entrada nueva bajo la clave nueva. No es necesario modificar `ReemplazarArchivoOriginalHandler` para esto — la invalidación es consecuencia pasiva del cambio de clave, no un borrado activo. Explícitamente fuera de alcance: una tarea de limpieza periódica de entradas huérfanas (el directorio puede crecer sin límite; se documenta como seguimiento, no se bloquea este change por eso).
- **Concurrencia**: un lock por clave de caché (nuevo `DocumentoPreviewCacheService` mantiene un `ConcurrentDictionary<string, SemaphoreSlim>` interno, uno por clave) evita que dos requests simultáneos sobre la misma versión del original disparen dos conversiones LibreOffice en paralelo — distinto del `SemaphoreSlim` global de `MaxConcurrentConversions` (ese limita cuántas conversiones corren a la vez en todo el proceso; este nuevo lock evita *duplicar* la conversión de la misma clave). Patrón: adquirir el lock de la clave → si el archivo de caché ya existe en disco, servirlo → si no, convertir+sellar+guardar → liberar.

### D5 — Auditoría: una sola entrada `VISUALIZACION` por apertura, registrada por el propio endpoint
El endpoint `/visor` SHALL registrar la entrada `VISUALIZACION` inline (mismo patrón que `ObtenerArchivoHandler`), nunca delegando al frontend un segundo `POST /:id/audit/access`. Esto evita el riesgo real de doble-registro: hoy coexisten dos mecanismos de auditoría de acceso (el genérico `POST /audit/access`, y el registro inline que ya hacen `ObtenerArchivoHandler` y `ObtenerArchivoOriginalHandler` cada uno por su cuenta) — el visor sigue el segundo patrón y el frontend **no** llama a `POST /audit/access` después de abrir el visor.

### D6 — Frontend: `react-pdf`, carga por blob autenticado, sin capa de texto, impresión vía iframe oculto
- Nueva dependencia `react-pdf` (pdf.js). Worker configurado para Vite con `pdfjs.GlobalWorkerOptions.workerSrc = new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url).toString()` — patrón estándar, sin CDN externo (esta app no tiene la restricción de CSP de un Artifact; es la app real).
- El componente pide el PDF con `api.get('/api/documents/:id/visor', { responseType: 'blob' })` (mismo patrón ya usado por `getArchivoOriginalUrl`/`getArchivoDistribucionBlob`/`exportarPdfControlado` — el interceptor de respuesta de `lib/axios.ts` ya sabe no desenvolver `responseType: 'blob'|'arraybuffer'`), y pasa el blob resultante a `<Document file={blob}>`. Nunca una URL string.
- `renderTextLayer={false}` y `renderAnnotationLayer={false}` en cada `<Page>` — sin capa de texto seleccionable ni anotaciones. `onContextMenu={(e) => e.preventDefault()}` en el contenedor del visor para desactivar el menú contextual (clic derecho → "Guardar imagen como" sobre el canvas).
- **Impresión (solo `JEFE_CONTROL_DOCUMENTARIO`/`ALTA_DIRECCION`)**: el botón de imprimir reutiliza el mismo blob ya cargado, crea un `<iframe>` oculto (`display:none` fuera de viewport, no `visibility:hidden` — algunos navegadores no imprimen contenido con `visibility:hidden`) con `src = URL.createObjectURL(blob)`, espera su evento `load`, llama `iframe.contentWindow.print()`, y remueve el iframe (+ `revokeObjectURL`) después de un breve delay o del evento `afterprint`. No hay botón de descarga en ningún punto del flujo de impresión — el diálogo nativo de impresión del navegador es responsabilidad del sistema operativo, fuera de control de la app (ver Riesgo R1).

### D7 — El modal de confirmación "pdf.previewTitle" de `DocumentActionPanel` NO se unifica con el visor
Son dos cosas distintas con propósitos distintos: ese modal es una confirmación cosmética (tarjeta HTML con metadatos) antes de una descarga real vía `exportar-pdf` (crea una "COPIA NO CONTROLADA" para llevar fuera del sistema, con hash y marca de agua reales, propósito: evidencia portátil). El visor nuevo es solo-lectura embebido, sin descarga, propósito: revisar sin sacar nada del sistema. Conviven sin cambios entre sí. (Confirmado con el código real — ese modal nunca renderiza un PDF, es JSX estático; no había nada que "unificar" en la práctica.)

### D8 — `document-pdf-security`/`documentPdf.ts` NO se toca; es código muerto, no una dependencia real
Se verificó por búsqueda que `requestDocumentPdf`/`requestDocumentView` (`src/utils/documentPdf.ts`, descritos por la spec `document-pdf-security`) **no están importados por ningún componente real** — fueron superados durante el cutover por `useExportarPdfControlado`/`useGetArchivoUrl` (`useDocumentActions.ts`), que sí hablan con el backend real. El `TODO: server-side PDF con marca de agua real y permisos restrictivos (RN-DOC-010)` de ese archivo sigue ahí, sin resolver, pero sobre código que ya no se ejecuta. Este change implementa la aplicación real de RN-DOC-010 desde cero en `document-viewer` (impresión restringida por rol, sin capa de texto) sin depender de ni modificar ese archivo muerto. Retirar `documentPdf.ts` y actualizar/retirar la spec `document-pdf-security` es limpieza correcta pero fuera de alcance de este change — queda como seguimiento sugerido, no como tarea aquí.

### D9 — El AUTOR tiene lectura (no edición) de su documento en PUBLICADO y OBSOLETO

**Tarea adicional (autor-lectura-publicado, 2026-10-08, decisión de Toño)**, plegada en este change porque `visor-documentos` todavía no estaba archivado.

Diagnóstico confirmado leyendo el código real: la matriz de permisos por `(estado, docRole)`, replicada carácter por carácter desde el PRD §4.2 tanto en el backend (`DocumentPermissionResolver.GetBasePermissions`) como en el frontend (`permissions.ts`), le asignaba a `AUTOR` `DenyAll` (sin `CanRead`) en `PUBLICADO` y en `OBSOLETO` — mientras que `REVISOR` y `APROBADOR` sí tenían `CanRead: true` en esos mismos estados, y `OPERARIO` también en `PUBLICADO`. El resultado era que cualquier usuario con acceso por confidencialidad podía leer un documento publicado, **excepto quien lo escribió**: no veía "Ver documento" en `DocumentActionPanel` (`canVerDocumento` evaluaba `perms.canRead` en `false`), el endpoint `/visor` rechazaba con 403 (`VisualizarDocumentoHandler`), y tampoco tenía `CanViewArchivoDistribucion` (deriva de `CanRead`).

**Decisión explícita de Toño**: el AUTOR SHALL tener acceso de lectura a su documento en `PUBLICADO` y en `OBSOLETO`, igual que REVISOR/APROBADOR. Se interpreta que el "Sin acceso" del PRD §4.2 se refería a **edición**, no a lectura. **Esta regla diverge a propósito del texto literal del PRD**, por decisión de Toño — no es un error de transcripción de la matriz, es un cambio deliberado sobre lo que el PRD decía.

Implementación — cambio mínimo y localizado, sin tocar nada más de la matriz:
- Backend: `GetBasePermissions` — `PUBLICADO` + `AUTOR` y `OBSOLETO` + `AUTOR` pasan de `DenyAll` a `DenyAll with { CanRead = true }`.
- Frontend: mismo cambio en `getBasePermissions` (`permissions.ts`).
- `canEdit`, `canDelete`, `canStartReview`, y cualquier otra acción de escritura permanecen en `false` para AUTOR en ambos estados — RN-DOC-003 (OBSOLETO de solo lectura) no cambia para nadie.

Efectos derivados confirmados (salen solos de `CanRead`, sin tocar su fórmula):
- "Ver documento" (visor) aparece para el autor en `PUBLICADO`, `EN_REVISION_PERIODICA` (ya lo tenía) y `OBSOLETO` (con el sello "OBSOLETO — No usar" de `document-viewer-api`). Ver también la actualización del Requirement "Permiso del visor" en `document-viewer-api/spec.md` (D2) — el `OR` con CA-34 para `OBSOLETO` ya no es necesario para `AUTOR`, solo para el caso restante (`docRole` sin `CanRead`, típicamente `OPERARIO`, con rol global `JEFE_CONTROL_DOCUMENTARIO`/`ALTA_DIRECCION`).
- `CanViewArchivoDistribucion` pasa a `true` para AUTOR en `PUBLICADO` (`basePermissions.CanRead && estado ∈ {PUBLICADO, EN_REVISION_PERIODICA}`) — habilita también `GET /:id/archivo-distribucion` (`ArchivoDistribucionHandler`, que gatea exactamente en ese flag) y el botón "Descargar PDF de distribución" en `DocumentDetailPage`.
- **No cambia** el acceso al archivo original: `CanViewArchivoOriginal`/`CanReplaceArchivoOriginal` (RN-DOC-013/016/018) solo aplican en `BORRADOR`/`EN_REVISION`, fuera del alcance de este cambio; `CanViewArchivoOriginalConCA34` (RN-DOC-014, usado por el endpoint real `GET /:id/archivo-original`) tampoco se tocó — el autor sigue sin poder descargar el original en `PUBLICADO`/`OBSOLETO`.
- Búsqueda confirmada de otros consumidores de `CanRead`/`canRead` para AUTOR: `ObtenerDocumentoHandler` (detalle) no gatea por `CanRead` en absoluto (solo nulea los campos de archivo original vía CA-34, sin relación con esta decisión); los handlers MSW de vincular/desvincular QE y NC gatean por `canEdit` (sin cambios); `GET /:id/archivo` (`DocumentoArchivoVigenteResolver`) no gatea la rama de distribución por `CanRead` en absoluto (acceso ya más laxo que el visor, sin relación con esta decisión).
- MSW: `getDocumentPermissions` es la misma función importada por los handlers (`documents.handlers.ts`) — el cambio aplica automáticamente, sin tocar ningún handler.

## Hallazgo de seguridad relacionado (no se resuelve en este change)

`DocumentoStorageService` guarda originales y PDFs de distribución bajo `wwwroot/uploads/documentos/{empresaId}/{documentoId}/...`, y `Program.cs` llama `app.UseStaticFiles()` **antes** de `UseAuthentication()/UseAuthorization()` — confirmado en el código real. Cualquiera que conozca o adivine la ruta exacta puede descargar esos archivos sin JWT, sin pasar por `CanAccessByConfidencialidad`, por la matriz de permisos, ni por el audit trail. Este change no agrava el problema (la caché de vistas previas vive fuera de `wwwroot`, bajo `ContentRootPath`, y el visor nunca construye ni expone una URL estática), pero tampoco lo resuelve. Se recomienda un change aparte, `almacenamiento-documentos-privado`, que mueva el storage fuera de `wwwroot` (o lo sirva solo a través de endpoints autenticados, como ya hace el resto de este módulo) — aplica también a `PlanoStorageService` (Locales), con el mismo patrón y el mismo riesgo.

## Risks / Trade-offs

- **R1 — Las restricciones del visor (sin descarga, sin copiar texto, impresión limitada) son disuasorias, no una protección absoluta.** Un usuario con conocimientos técnicos puede extraer el PDF desde las DevTools del navegador (la respuesta blob ya está en memoria), o usar "Guardar como PDF" en el diálogo de impresión nativo si llega a tener acceso al botón de imprimir. La protección real es el control de acceso del endpoint (`CanRead`/CA-34 + confidencialidad + tenant, verificados en cada request) y el audit trail (`VISUALIZACION` queda registrado con el actor real) — no el visor en sí. → Mitigación: ninguna adicional en este change; se deja explícito para que nadie asuma que el visor es una DRM real.
- **R2 — La caché de vista previa puede crecer sin límite** (una entrada por cada reemplazo real de archivo original, nunca borrada activamente). → Mitigación: aceptado como trade-off explícito (mismo criterio que ya rige los originales archivados); una limpieza periódica queda fuera de alcance, documentada como seguimiento futuro.
- **R3 — El sellado de "VISTA PREVIA"/"OBSOLETO" con PdfSharpCore puede fallar en algún PDF generado por una versión particular de LibreOffice** (mismo riesgo ya aceptado y documentado para `SellarPublicado`, que degrada sirviendo el PDF sin sello en vez de bloquear). → Mitigación: aplicar la misma degradación (log de error + servir sin sello) en vez de un 500, consistente con el precedente ya establecido en `FirmarPublicarDocumentoHandler`.
- **R4 — Impresión vía iframe oculto es un patrón con comportamiento inconsistente entre navegadores** (algunos bloquean `contentWindow.print()` sin interacción directa del usuario, o tardan en disparar `load` para un blob URL). → Mitigación: el botón de imprimir se dispara desde un click real del usuario (no automático), y se agrega un fallback visible (mensaje de error) si `print()` no está disponible o lanza.
